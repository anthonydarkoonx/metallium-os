# Metallium-OS handoff (rewritten 2026-11-16)

## Where things stand
Metallium-OS is a Rust `no_std` AArch64 microkernel (QEMU `virt`; a ROCK 3C board port lives in the separate GPL-2.0-only repository `metallium-os-rock3c` (formerly `rock 3c test/`; see its `README.md`).
**There is no window system in the tree.** The OS is meant to be paired with a separate window manager or desktop environment (see `docs/DESKTOP-INTERFACE.md`).
**What the screen shows now:** `user/src/screen.rs` is a stub: a backdrop with the terminal (`user/src/shell.rs`, `console.rs`, drawn with the bitmap font in
`libs/metallium-gfx`) centred on it, keyboard input only. `make run-window` boots to it (checked by screenshot on QEMU).
**Kept:** kernel, drivers (`gpu.rs`, `kbd.rs`, `blk.rs`, `netdrv.rs`, board overlay), `metallium-gfx` (only for the terminal's font and a few drawing calls), `metallium-input`,
`metallium-edit` (terminal editor), `metallium-map`, `metallium-ed25519`, the storage, net and compression libs, the program manager and the terminal.
**Naming (2026-11-17):** the screen task, once "the desktop", is now the **console** (role 13, task name `console`, `kernel/src/devices.rs` `Phase::Console`, `CONSOLE_HEAP_PAGES`, `user/src/screen.rs`, `INFO_CONSOLE`, `programs::console_session()`). The role number 13 and the board's `DESK_*` display constants keep their numbers.
**Desktop seam (2026-11-17):** `make run-window DESKTOP=<path to a desktop repo>` links that repo's `metallium-desktop-boot` into the screen task (`user/src/screen.rs`, `#[cfg(desktop)]`) and puts its packages in the image, installed by default (`/system/etc/program-defaults`, `role = desktop`); see `docs/DESKTOP-INTERFACE.md`. Default builds are unchanged. With `../metallium-os-desktop` the compositor, taskbar and Start menu boot on QEMU; the other desktop programs are not packaged yet.
**Display endpoint:** the display endpoint that `progmgr` still hands to programs with the `window` permission (`docs/PROGRAMS.md`, `metallium-map`'s permission list).
**Memory safety (2026-11-17):** see `docs/BOARD-SYNC.md` and the git log. Miri passes on all the libs' tests; the long ones run reduced under Miri (`cfg!(miri)`: strided byte sweeps, 2 RFC 8032 vectors, 2,000 loader images; native counts unchanged). Deny-level lints `unsafe_op_in_unsafe_fn` and `clippy::undocumented_unsafe_blocks` apply to every crate (`make clippy`). Every `unsafe` site has a SAFETY comment; the kernel's lock-free globals are borrow-checked at run time (`kernel/src/sync.rs`); the board runs the new kernel (self-test 88/13/1, same as before).
**Encrypted data volume (2026-11-20):** `libs/metallium-crypt` (HMAC-SHA512, PBKDF2, the volume header with four key slots, block sealing; tests against RFC 4231 and Python's hashlib), `user/src/storage.rs` (`EncDev`: the store's blocks are 9 sectors, ciphertext plus a metadata sector; `Vol` states plain / locked / open / damaged; `volume_call`: `LFS_STATUS`, `LFS_UNLOCK`, `LFS_SET_PASSPHRASE`), `user/src/vfs.rs` (waits for the unlock before it reads `/data`), `user/src/greeter.rs` (the built-in prompt, shown by the screen task, and the `GREETER=` seam, docs/GREETER-INTERFACE.md), kernel `DEVICE_SECRET` (syscall 46, store server only; QEMU: fw_cfg `opt/metallium/device-secret`; board: `device_secret()` returns `None` until the RK3566 OTP is read, so board volumes stay plain). `docs/ENCRYPTION.md` has the format, the policy and what is not done. Tests: `make volume-test` (six boots of one disk), `make qemu-test-encrypted` (the whole suite on an encrypted volume; `tools/checkdisk.py` knows the header). The LFS `mount` now treats a checkpoint block that does not authenticate as an invalid checkpoint (the other may be good).

**`/data` directory table (2026-11-20):** the table was one 4 KiB block with 51 entries and 64-byte paths for the whole machine; it is now `VFS3`: 1024 entries of 144 bytes over 37 blocks (`META_KEY`, then `META_MORE + b`; journal blocks `JOURNAL_KEY`, `JOURNAL_MORE + b`), paths up to 127 bytes, and a commit rewrites only the blocks whose bytes changed (hash cache). A `VFS2` table is read as before and replaced by the first commit. The in-memory arrays are `Vec`s (they no longer fit the stack). `make table-test` (`only=12`) covers migration from a crafted `VFS2` table, 300 files across restarts, and long paths. This was the first obstacle of the multi-user plan (`docs/MULTIUSER-PLAN.md`).

**Multi-user, phase 1 (2026-11-20):** per-scope entry quotas and inherited confinement in the VFS (`V_SCOPE` w2 = quota, path `/data` = the same scope as the caller's; `Command::quota`, manifest `quota`), `programs/src/bin/sessiond.rs` (accounts, login, a confined session per user; `homeprobe` is the stand-in session payload) and `make session-test`; see `docs/MULTIUSER-PLAN.md` *Status*.

**Board, RAM and serial loading (2026-11-21):** the kernel sees all RAM on the ROCK 3C (7680 MiB from the DTB banks, `platform::ram_hole`, `DMA_LIMIT`, direct map skips holes, cache maintenance by VA, `frame::cache_va`); `fetch` shows the real GPU/storage/IOMMU names (`gpu_name`, `storage_name`, `iommu_note`). Encrypted per-user volumes, `sessiond`, the greeter seam and the public `metallium-greeter` repo (`~/Desktop/greeter`) are done and tested on QEMU. **Serial loader protocol 2** (board repo, `metallium/overlay/kernel/src/platform/kloader_proto.rs`, `scripts/metallium-load.py`, `scripts/test-load-protocol.py` with `scripts/loadproto-test`): numbered 1 KiB chunks, CRC-32, cumulative acks, go-back-N resends, zero runs as one frame; the sender detects an old loader (no "(v2)" in the banner) and bootstraps through it. On the real board: 12 MiB disk in 5.8 s, kernel in 11.2 s, 0 resends; the SD card's `/metal.img` carries the v2 kernel (written 2026-11-21, sha256 checked). Push with `python3 scripts/metallium-load.py --disk <disk.img> metallium/out/metal.img` (add `--reset` to cycle the board; `--wait N`). Board repo at b5b0645, OS repo at 48ea58a, both pushed.

**Device tree, GICv3, cores, USB (2026-11-20):** `libs/metallium-fdt` reads the device tree firmware passes in x0 (RAM size, cores and their MPIDRs and speeds, interrupt controller, PSCI conduit); the kernel is also built as a flat Linux-style `Image` (`metallium-kernel.img`, header in `boot.S`), which is what makes QEMU and boot loaders hand the tree over (an ELF gets none; the kernel then falls back to fw_cfg and probing). `platform/qemu_virt/gicv3.rs` is a GICv3 driver (`make GIC=3`); `Intc` picks v2 or v3 at run time from the tree. `MAX_CPUS` is 32 (2026-11-20, later: every core but the boot core gets its stacks from RAM when it starts: 16 KiB emergency stack, 16 KiB unmapped guard, 64 KiB stack in one run of pages, `smp::make_stacks`; the guard comes out of the identity map with `mmu::unmap_kernel_pages`, which first turns a 2 MiB block into 4 KiB pages if it must, so all stacks are made before any other core runs; boot.S reads `CORE_STACK_TOP` / `CORE_EMERG_TOP`, and PSCI's context id carries the stack top and core number to `_secondary_start`; the image shrank by 1 MiB); the real count comes from the tree (`make qemu-test GIC=3 SMP=32`; `make stack-guard` also overflows core 31's stack). Without a tree the firmware is asked how many cores there are (PSCI AFFINITY_INFO) and the controller which GIC it is (GICD ID register: v2's at 0xFE8, v3's at 0xFFE8; a v2 faults on the second, so v2 is asked first), and a core's MPIDR is guessed the way QEMU numbers them (16 to a cluster); `make elf-boot-test` boots the ELF on GICv2 with 8 cores and on GICv3 with 32. Which cores are efficiency cores comes from `capacity-dmips-mhz` when the cores differ, else the old model (0 and 1 little). SYSINFO pages 10, 11, 13, 14 take 16-bit task ids (`arg` layouts in docs/ABI.md; holder masks are per window of 64 tasks). The scheduler's idle check, sleeper wake-up and the revoke sweep no longer scan every slot (`LIVE` mask, `NEXT_TIMED` hint, free slots skipped). **Per-priority run queues were not built:** a task's level is derived (class, inheritance, the best caller queued at its endpoints), not stored, so there is nothing to keep a queue ordered by; under 400 CPU-bound programs a candidate search looks at about 340 ready tasks (`[sched] ... candidate searches` line, `make scale`) and the 10 ms sleep of the conductor still wakes in 100 ms. USB: `libs/metallium-usb` (descriptor, HID report, key parsing; host-tested) and `user/src/xhci.rs` (xHCI driver run by the input task, polled): keyboards and pointers on root ports or behind hubs (full/high-speed hubs, three tiers, route strings, transaction-translator fields), hot plug and unplug (port-change events and the hub's status endpoint), key repeat (500 ms, then 30 Hz), EP0 packet size from the device descriptor, Disable Slot and zeroed memory when a device goes. Up to 16 devices at once (2026-11-20, later: was 6; 80 pages of USB memory; `make usb-test-many`: a hub with seven keyboards and two more devices). Not done: SuperSpeed hubs, one-TT-per-port hubs (QEMU has neither, so they could not be tested). **Blocking input (2026-11-20, later):** `INPUT_WAIT` (proto 72: `w[1]` = longest wait in ms, at most 1000; the reply is `INPUT_POLL`'s) lets a desktop sleep until input arrives instead of polling on a timer; with only a USB controller the driver sleeps on the controller's INTx line (`IRQ_USB` 3, driver slot 10, `Usb::wait`; the line is level triggered and cleared by `poll`), with virtio-input devices it looks every millisecond (those are polled). The driver does nothing else while it waits. `make usb-test` has a client that waits and checks it is woken by the input, not by its time limit. This also fixed an old bug: the input driver had its endpoint (slot 0) only when a virtio-input keyboard was present, so on a USB-only machine nobody could call it (the driver spun on a failing `recv`); `boot_caps` now gives role 14 the endpoint. A stale transfer event of an unplugged device is dropped when its slot is released (it could be taken for a new device given the same slot number). `make usb-test` (flat: types, clicks, holds a key, plugs a keyboard in and out), `make usb-test-hub` (everything behind a hub) and `make usb-test-noncoherent` drive it through QMP. Code review of the device-tree/GICv3/USB work found and fixed: session 255 colliding with the "no session" marker (sessions now 8..255), a lost-wakeup race in the sleeper hint (the task's mask bit goes in before its deadline), a rejected USB device keeping its slot and memory, EP0 packet size, the FDT version check, and the no-tree core count.

**Session pages (2026-11-20):** file and network sessions are a quarter of the task slots, 8 to 255 each (`obj::sessions_for`; SYSINFO 18 reports them). The pages are one contiguous object per server (VFS slot 16, `netd` slot 16, mapped once); each program's cap is a one-page object over the same frames (ids 64.. and 320..). One capability slot per server instead of one per page.

**Scale limits, step 1 (2026-11-19):** RAM up to 255 GiB (was 256 MiB tracked, 1 GiB accepted): frame tables carved from RAM at boot, TTBR1 direct map for RAM above the first GiB, `[mem] TEST RAM above the first GiB ...` self-test. Checked: `make qemu-test` ALL PASS (64 MiB, 4 CPUs), `make kaslr` ALL PASS, headless boots at 1 GiB and 4 GiB (the self-test passes at 4 GiB). **Not done:** the QEMU test suite is written for 64 MiB; at 256 MiB and up its memory-pressure tests (pager, swap, compactd) fail or run out of the conductor's heap quota, so larger sizes are boots, not suites. Per-owner frame lists are done (18 bytes of table per frame; `count_owned` is O(1), `free_owned` walks only the owner's frames; boot self-test `owner_lists_selftest`; `make qemu-test` and `make chaos` pass). **Task slots and teardown (2026-11-19):** the task table is sized at boot (`task::tasks_for`: one slot per MiB of RAM, 64..1024, or fw_cfg `opt/metallium/max-tasks`); per-task state is carved from RAM (`kernel/src/table.rs`: `Table`, `SlotTable`). Task ids are `u16` everywhere (frame owners, endpoints, parents, nodes); the scheduler's ready/timed/RT sets are multi-word masks; lock ranks and the node pool (8192) scale with it. `World` no longer locks every task: a teardown takes the *lifecycle* lock (`task::lifecycle`, also held by SPAWN, WAIT, THREAD_CREATE, TASK_START, CAP_GRANT and RESTORE_OF), kills nodes first (`cap::kill_subtree`) and sweeps tasks one lock at a time (see the comment on `TEARDOWN` in `task.rs`). Checked: `make qemu-test`, `qemu-test-up`, `chaos` (seeds 1, 2), `fuzz` (seeds 1-3), `kaslr`, and the new `make scale` (997 programs in a 1024-slot table). I also gave the one-core run its missing 'skipped: one core' lines, so `make qemu-test-up` passes again (it had been failing since commit 4685770). **Endpoints and objects (2026-11-20):** both tables are boot-sized (`ipc::eps_for`, `obj::objs_for`; ids are `u16`; ranks leave room for `ipc::MAX_EPS` = 4400 endpoint locks); `make scale` starts every slot with 4 endpoints and 2 objects. Two performance fixes came out of it: spin-lock release only executes `sev` when a core is waiting (`SpinLock::waiting`), and the scheduler reads a task's class and pinned core from atomics (`task::class_of`, `pinned_of`) instead of taking the checked read-borrow of `INFO` for every candidate (with ~1000 ready tasks that borrow's shared read-modify-write made every scheduling decision take milliseconds: kills ran at 30-170 ms each, now 1.8 ms). A death now sweeps the tasks once for all its capabilities (`World::reset`), finds its servers through its own links instead of scanning, and touches only the endpoints it can receive on or has queued calls on. **Still limits at 1000 tasks:** `MAX_CPUS` (4), the scheduler's per-decision scans are O(ready tasks), a revoke sweeps every task slot (about 8 us each), task-manager SYSINFO pages 10-13 only see tasks below 256 (bit masks: below 64). Programs' consumers of `SYSINFO` page 5 now see parent 0xFFFF, not 255, for none.

## Kernel layering (framekernel style, 2026-11-13)
The kernel has a *frame* (`kernel/src/frame.rs`: `phys` = bounds-checked physical RAM access, `cpu` = system registers / wfe / semihosting) plus the other framework modules that still use `unsafe` (`mmu`, `smmu`, `gic`, `trap`, `smp`, `sync`, `timer`, `cache`, `kaslr`, `pci`, `platform`, `uart`, `virtio_rng`, `main`, `boot.S`). These 15 modules carry `#![forbid(unsafe_code)]`: `cap ipc compact irq mem ring swap obj spawn syscall pager thread task sched rand`. Rules: new raw-memory or register access goes into `frame`; addresses a user program chose use the `try_*` forms (a device page is not RAM; never panic on user input). `sync::Global::get()` returns a run-time-checked guard (`RefMut`), so an overlapping borrow is a kernel panic, not two live `&mut`; the unchecked `boot_get` is `unsafe` (only `mmu::init`). Checked with a build and one headless `ui-probe` boot, not the QEMU suites. Next (not started): measure IPC (benchmark endpoints 6..15 exist), then direct hand-off / fewer round trips.

## Gotchas
- **No atomic read-modify-write before the MMU is on.** With the MMU off every access is Device memory; on the RK3566 an atomic there is a data abort (ESR DFSC 0x35), but QEMU allows it, so the QEMU suite cannot catch this. `mmu::init` therefore uses `Global::boot_get` (plain access), not the checked `get`. Run the board self-test after any change to early boot.
- The project was renamed Metallium-OS on 2026-11-20 (folder `metallium-os`, GitHub repository `anthonydarkoonx/metallium-os`; the old URL redirects). The crates (`metal-*`), the `opt/metallium/...` fw_cfg names and the separate board and desktop repositories (`metallium-os-rock3c`, `metallium-os-desktop`) keep their names. After a folder rename `touch user/link.ld programs/link.ld programs/link-pie.ld kernel/linker.ld`.
- The folder used to be called `Metal OS`. If `make` fails with `cannot find linker script /home/computer/Desktop/Metal OS/user/link.ld`, cargo has cached the old path. `touch user/link.ld programs/link.ld programs/link-pie.ld kernel/linker.ld` and rebuild. Checked 2026-11-12: after that, `make run` boots (KASLR moves the kernel, virtio-rng is folded in, the boot tasks start).
- Never run two `make` jobs at once (they share `disk.img` and ports). A killed make can leave QEMU or `tools/netpeer.py` holding ports 18077/7002, so check for leftovers first.
- When waiting, loop on `pgrep -x make`. `pgrep -f "make qemu-test"` matches its own shell wrapper and never ends.
- No GPL-derived code, clean-room only. Ask before reading Linux sources.
- Scope is QEMU-only, general-purpose kernel work.
